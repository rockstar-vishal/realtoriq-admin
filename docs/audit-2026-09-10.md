# Audit — 10 September 2026

Eight parallel auditors over tenancy, authentication, money, authorization,
uploads, data integrity, production readiness and API contract. **72 findings
raised; the 8 most severe were adversarially re-checked and all 8 survived.** I
then independently reproduced a sample against staging — including two I
initially believed were false.

Everything below cites a file and line, and most were reproduced with a live
request rather than read off the source.

## The one to fix first

### 1. All three hard money blocks are read-then-write with no lock and no DB constraint — concurrent requests walk straight through them

**CRITICAL** · `app/services/bookings/raise_invoice.rb:22`

Two or more invoice POSTs that arrive within the same few milliseconds each read `booking.invoiceable_balance` before any of them has INSERTed, each independently passes `amount > available`, and all of them save. A booking whose net income is ₹1,00,000 ends up with ₹3,00,000 invoiced. The identical shape defeats `over_collected` and `over_collected_for_invoice` in record_collection.rb:24-31 — an invoice for ₹1,00,000 ends up with ₹3,00,000 collected against it. A double-tap on a slow mobile connection, or a retry after a timeout, is enough; no malice is needed.

**Fix.** Do the check and the insert under a row lock: wrap the body of RaiseInvoice#call and RecordCollection#call in `booking.with_lock do … end` so the balance is re-read inside the transaction that writes; for `over_collected_for_invoice` lock the invoice row too (`invoice.lock!` inside the same transaction). Belt-and-braces: an exclusion/trigger or a `remaining_balance` counter column on bookings with a `CHECK (… >= 0)` so the database refuses the third write even if a code path forgets the lock.

> Reproduced on staging: a booking with `net_income` ₹1,00,000 accepted **two**
> invoices of ₹1,00,000 fired concurrently, ending at `invoiced 200000,
> invoiceable_balance -100000`. The same shape defeated `over_collected` (three
> of eight concurrent collections landed) and `over_collected_for_invoice`.
>
> What makes it critical rather than merely wrong: **there is no repair path in
> the app.** `config/routes.rb` gives invoices and collections `index` and
> `create` only — no update, no destroy — and `docs/api.md` records that
> cancelling an invoice was never built. One double-tap on a slow connection
> permanently leaves a firm's books with `invoiced > net_income`, and every
> money query and report sums it.

## Also confirmed

### 2. POST /auth/verify 500s when `device` is not an object — and the one-time code is already burned, so sign-in becomes unrecoverable

**HIGH** · `app/controllers/api/v1/auth_controller.rb:111`

A client that sends `"device": "iPhone 15"` (a string) or `"device": ["a"]` (an array) instead of an object gets a 500 on every sign-in. `device_params` runs AFTER `record.verify` has consumed the code (auth_controller.rb:56) and after `clear_otp_lockout!` (line 68), so the code is spent before the crash. The user retries with the same request_id, which now counts as a failed attempt — three retries and `register_failed_otp_attempt!` locks the account for 30 minutes. The user is stuck in a 500 loop they cannot escape, with no error code the app can switch on, and the endpoint is unauthenticated so anyone can trigger it.

**Fix.** Coerce before permitting: `raw = params[:device]; return {} unless raw.respond_to?(:permit)` (or `params.expect(device: [...])` guarded by `is_a?(ActionController::Parameters)`), and add a `rescue_from ActionController::ParameterMissing`-style guard so a malformed device never reaches AuthSession.start!. Better still, build `device_params` before `record.verify` so a bad payload cannot burn the code.
### 3. PATCH /leads/:id performs the manager-only reassign — `assigned_user_id` is in the permit list with no role guard and no firm check

**HIGH** · `app/controllers/api/v1/leads_controller.rb:167`

An agent PATCHes a lead they own with {"assigned_user_id": "<manager id>"} and gets 200 — the exact write POST /leads/:id/assign refuses with 403 forbidden_role one second earlier. Three consequences: (1) an agent silently reassigns leads, including handing one to another user or unassigning it (assigned_user_id: ""), which hides it from every agent in the firm; (2) unlike `assign`, this path never resolves the id through `current_firm.users.active`, so an agent can bind the lead to a user in ANOTHER firm — the API then renders that outsider's name inside this firm's lead payload; (3) a non-existent uuid hits the `leads_assigned_user_id_fkey` and escapes as an unhandled 500 HTML page instead of the JSON error envelope.

**Fix.** Stop accepting `assigned_user_id` on the update path: remove it from `lead_params` and give `create` its own permit list (Leads::Create legitimately takes it — docs/api.md:296). Every write of the column should go through one resolver that both guards the role and scopes the lookup, i.e. reuse `assign`'s `current_firm.users.active.find_by(id: ...)` and its `unknown_user` 404, so a foreign or unknown id can never reach the column and can never raise ActiveRecord::InvalidForeignKey.
### 4. Booking documents and collection proofs are served on permanent, unauthenticated URLs

**HIGH** · `app/serializers/api/v1/blob_url.rb:16`

BookingSerializer emits `documents[].url` and CollectionSerializer emits `proof_url` through BlobUrl, which builds `rails_blob_url` — Rails' ActiveStorage::Blobs::RedirectController. That controller has no authentication, and because `config.active_storage.urls_expire_in` is never set anywhere in config/, the signed_id in the path never expires. The API gates these endpoints to manager/super_admin because they are commission records (app/controllers/api/v1/booking_documents_controller.rb:6, app/controllers/api/v1/collections_controller.rb:6, and the routes.rb comment 'Managers and super admins only — these are commission records'), but the file itself is world-readable to anyone who ever sees the link: an agent who was told 'no', a removed employee, a link pasted into a chat, a proxy log. Revoking the user's session does nothing.

**Fix.** Photos can stay public (that is what `shareable` is for), but booking documents and collection proofs must not use BlobUrl. Serve them from a controller under AuthenticatedController that checks the firm and role and then returns `blob.url(expires_in: 5.minutes)`, or redirects to it. As a minimum stop-gap set `config.active_storage.urls_expire_in` so a leaked link dies.
### 5. Editing a booking recomputes net_income with no check against invoices already raised — the documented "hard block" is bypassable with one PATCH

**HIGH** · `app/controllers/api/v1/bookings_controller.rb:127`

Raise the full ₹4,50,000 of brokerage against a ₹1 Cr booking, then PATCH agreement_value down to ₹1,00,000. net_income is silently recomputed to ₹4,500 while ₹4,50,000 of invoices stay on record — the booking is now invoiced 100x past what it earned, and invoiceable_balance is −₹4,45,500. docs/schema.md calls this an enforced hard block ("an invoice may not take the booking past its net income"); it is enforced only at the moment an invoice is created, never when the figure it is measured against changes.

**Fix.** In BookingsController#update / a Bookings::Update service, reject the change when the recomputed net income would fall below booking.invoices.where(status: :raised).sum(:amount), returning the same over_invoiced error shape with the arithmetic in details. A DB CHECK cannot express this (it spans two tables), so the guard has to live with the write — and it belongs next to the RaiseInvoice guard, not only inside it.
### 6. config/database.yml is gitignored and untracked — production cannot boot from a clean checkout

**HIGH** · `.gitignore:40`

Clone the repo on a production box (or run `docker build`), set RAILS_ENV=production, and boot: Rails raises `Cannot load database configuration: Could not load database configuration. No such file - config/database.yml` before any initializer runs. It also kills the image build at Dockerfile:50, which boots the app in production to precompile assets. Only config/database.yml.sample ships.

**Fix.** Commit a config/database.yml that is safe in git — it already emits host/username/password only from ENV (lines 65-73), so nothing secret is in it — and keep database.yml.sample as documentation, or drop the sample. If it must stay ignored, ship it through Kamal `files:` and say so in the deploy docs.
### 7. Gemfile.lock was deleted from the repo and gitignored — the Docker build fails at COPY, and BUNDLE_DEPLOYMENT=1 requires it

**HIGH** · `.gitignore:12`

`docker build -t kgen_realtoriq_admin .` on a clean clone (the command in Dockerfile:5, and what `kamal deploy` runs) fails at Dockerfile:38 `COPY Gemfile Gemfile.lock ./` — the file does not exist. If someone drops in a locally generated lockfile, Dockerfile:24 sets BUNDLE_DEPLOYMENT="1", which aborts if the lockfile is missing or out of sync with the Gemfile. And with no committed lockfile, whatever versions resolve at build time are what production runs — not what staging and the specs were run against.

**Fix.** Remove line 12 from .gitignore and commit the current Gemfile.lock (`git add -f Gemfile.lock`). A Rails app deployed with Bundler deployment mode cannot work without it.
### 8. A 422-rejected PATCH silently destroys the record's typologies (leads and projects)

**HIGH** · `app/controllers/api/v1/leads_controller.rb:49`

PATCH /leads/:id with typology_ids plus any field that fails validation: the typologies are destroyed, the save is rejected, nothing is rolled back. Live on staging: lead L-0034 had [1 BHK, 2 BHK]; one PATCH with {"typology_ids":[1 BHK],"budget_min":9000000,"budget_max":100} returned 422 "Budget max must be greater than or equal to the minimum budget" and a re-read showed "typologies": []. Same on projects: an AUDIT project with one typology, PATCHed with {"lat":999,"typologies":[...]}, returned 422 "Lat must be in -90..90" and re-read as typologies [], price_band null, area_band null — the whole pricing band gone. The client shows a field-level validation error, the user corrects the field and resubmits, and the configurations they never touched are already lost.

**Fix.** Wrap assign + replace + save in a single `ActiveRecord::Base.transaction` and `raise ActiveRecord::Rollback` when the save fails, or validate first (`@lead.valid?`) before touching the join rows. Leads::Create already does its multi-write inside `Lead.transaction`; update does not.


## Reproduced by me, from the unverified pile

These were raised but not adversarially checked, so I ran them myself:

- **`page=0`, `page=`, `page=abc`, `page=-1` return a 500 HTML page on every
  index endpoint** — `/leads`, `/projects`, `/bookings` all confirmed. A client
  that sends `page=0` for its first page, or an empty string from an unset form
  field, gets a 500 instead of a list. (`per_page` is safe — it was hardened
  earlier.)
- **`GET /leads?typology_ids[]=<id>` — a filter this project documents — 500s on
  the default sort**, and returns 200 with `sort=recent`. So the documented
  filter is broken in exactly its default configuration.
- **`booked_on` is documented as required but silently defaults to today.**
  Posting a booking without it returns 201 with today's date. That is a mistake
  in `docs/api.md` (mine), and it means a near-miss key lands the booking in the
  wrong month for every report.

## A note on the audit itself

The auditors were told not to delete or cancel anything, and they did not. But
proving the concurrency bug **required creating** the corruption it describes,
and I had not anticipated that: staging now carries six bookings with
inconsistent books, and one auditor PATCHed the seeded demo booking **B-0001**
down to a tenth of its value to demonstrate the `net_income` recompute.

B-0001 is repaired — back to ₹1,56,00,000 at 4.5%, `net_income` ₹6,86,000. The
six probe bookings are still there and still distort the firm's totals. They can
only be cancelled, never deleted, because that is the one lever the API offers.
